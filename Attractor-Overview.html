Attractor Overview

Attractor is Milton's receipt-first, content-addressed provenance substrate for multi-agent knowledge work. It turns evidence into auditable claims, emits reviewable manifests, and lets the wiki stay human-readable without becoming the trust anchor.

Why Attractor Exists

Milton has many agents, hosts, issues, PRs, chat channels, and wiki pages. The hard problem is not only storing facts. The hard problem is knowing which claims came from which source bytes, which agent or process promoted them, whether another agent can reproduce the result, and whether a later cleanup changed meaning or only presentation.

Evidence stays evidence
Raw issue, wiki, PR, and chat material is not canonical until a typed projector promotes it.
Identity converges
Content-derived identity makes duplicate values converge instead of multiplying silently.
Provenance is first-class
Source spans and receipts are part of the data model, not a footer convention.
Output is reviewable
Wiki pages, HTML, and audit manifests are projections humans can inspect before publish.

Core Concepts

ConceptMeaning in Attractor
Cell / value nodeA content-addressed unit of evidence or derived data.
ProvenanceThe source issue, wiki page, chat span, PR, command, or run that produced a value.
ProjectorA typed boundary that turns raw evidence into structured claims and emits a receipt.
RelationA typed edge such as page -> source_issue, claim -> source_span, or page -> duplicate_of.
ReceiptA reproducible record of inputs, projector version, output hashes, and validation status.
ManifestA reviewable output such as wiki-audit.jsonl, taxonomy maps, duplicate reports, or HTML navigation data.

What It Does For The Wiki Cleanup

→

Reviewed HTML / wiki output
  1. Inventory wiki pages, issue sources, and later chat archive snapshots.
  2. Map identity from old page names to canonical topic IDs and redirects.
  3. Detect cleanup targets such as duplicates, orphan pages, missing summaries, stale categories, and unreviewed chat-derived claims.
  4. Bind sources with issue snapshot hashes and chat span receipts.
  5. Emit manifests for human review before any wiki rewrite.
  6. Generate HTML navigation from reviewed taxonomy data so presentation cannot drift from canonical content.

Threat Model

Attractor gives tamper-evident provenance against rewrite, reorder, truncation, or appended forgery given an honest externally persisted head or receipt. It does not magically prevent a coordinated rewrite of both the chain and the trusted head. Content addressing proves value identity; receipts and externally pinned heads make later verification possible. The trust boundary must be named in every published workflow.

Relationship To Graph Databases

A graph database is a general query and traversal substrate. Attractor is a convergence and trust substrate. They compose: Attractor can produce a verified graph snapshot that a graph database later indexes for ad-hoc traversal. But the first requirement for Milton is receipts, provenance, and reproducibility; the query layer comes after the evidence layer.

  • GraphDB answers: what is connected to what?
  • Attractor answers: what claim was derived from what bytes, through what projector, with what receipt?

Practical Rule

If a future agent cannot answer “what exact bytes produced this claim, through what projector, at what version, with what receipt?” then the claim is not ready to become canonical wiki knowledge.

Non-goals

  • Attractor is not the canonical wiki editor.
  • Attractor is not a free-text scraper that promotes uncited claims.
  • Attractor is not a magic immutable ledger without an honest head.
  • Attractor is not a generic replacement for all graph databases.
  • Attractor should not write wiki pages blindly; it should emit reviewable manifests and receipts first.
