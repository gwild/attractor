Attractor is not a replacement for graph databases. It is a receipt-first convergence and provenance layer that can feed a graph database when a project needs richer traversal, visualization, or query performance.

The short version: a graph database answers "what is connected to what?" Attractor answers "what exact evidence produced this claim, did equivalent values converge, and can we replay the projection that promoted it?"

Comparison

Dimension Attractor Generic Graph Database
Primary job Preserve evidence, convergence, receipts, and projection history. Store and query nodes and edges efficiently.
Trust anchor Content hashes, source spans, projector versions, append-only receipt chain. Database state plus application-level conventions.
Identity Content-addressed values such as blake3(content). Usually database-assigned IDs or application-assigned IDs.
Duplicate handling Identical content converges to one value with a provenance multiset. Duplicates are possible unless the application enforces uniqueness.
Provenance Required for promotion; every claim must point back to source bytes. Optional unless schema and application code require it.
History Ordered receipt/event log with tamper-evident checks. Often mutable current state; history requires audit tables or event sourcing.
Write path Typed projector boundary; raw prose cannot become canonical by accident. Application code writes graph records directly.
Read path Emits reviewable manifests, Markdown, HTML, exports, and query snapshots. Query language and graph traversals are first-class.
Best first use Source receipts, duplicate detection, claim promotion, audit manifests. Exploratory graph queries, path finding, dashboards, recommendations.

Why Not Just Use Neo4j, RDF, Or Another Graph Store?

Many organizations do not first fail because they cannot traverse edges. They fail because documents, chats, tickets, logs, and reviews contain overlapping claims with unclear source boundaries. A graph database can represent the result, but it does not by itself enforce the receipt contract that makes the result trustworthy.

Attractor should therefore sit before the query database:

  1. ingest evidence snapshots;
  2. project typed claims with source spans;
  3. converge identical values;
  4. append receipts;
  5. emit a reviewed graph snapshot;
  6. optionally load that snapshot into a graph database.

Duplicate Content Example

Two people or agents may write the same durable claim in different places:

Source Text
Ticket comment Renamed documentation pages must preserve redirects.
Chat message Renamed documentation pages must preserve redirects.

A generic graph database might store two Claim nodes unless the application deduplicates them. Attractor stores one value and two provenance entries:

value_id = blake3("Renamed documentation pages must preserve redirects.")
provenance = [
  ticket:1234#comment-9 span 14-22,
  chat:#docs:msg-32807fa9 span 1-1
]

That distinction matters when an editor later asks whether a statement is independently supported, copied from one source, or stale.

Projection Boundary

Attractor's most important boundary is the projector:

Input Projector Requirement Output
Raw chat Message ID, channel, sender, timestamp, quoted source span. Candidate claim, not canonical prose.
Issue or ticket Item/comment ID, API receipt, source span. Claim, task relation, or migration candidate.
Document page Commit, path, byte hash, heading/span. Page relation, duplicate signal, or missing-summary signal.
Command/test run Command, cwd, commit, exit code, output digest. Validation receipt.
Dataset row Dataset snapshot, row ID, schema version, cell span or digest. Structured evidence node.

The projector must fail closed when it cannot produce source-span receipts. A graph database can store the output, but the projector is what prevents unsupported prose from becoming knowledge.

When A Graph Database Still Helps

A graph database becomes useful after Attractor has produced a verified snapshot. Good follow-on uses include:

  • traversing document-to-ticket-to-chat evidence paths;
  • finding clusters of duplicate or near-duplicate pages;
  • visualizing ownership and review paths;
  • answering "what pages are blocked by this issue?";
  • ranking missing summaries by source density;
  • powering dashboards and search facets.

Example: Milton Migration

In the Milton issue migration, Attractor-style receipts bind migrated wiki pages back to exact GitHub issue snapshots and wiki commits. A graph database could later query the resulting page, issue, and chat relations, but Attractor's load-bearing role is proving how each migrated claim or page was produced.

Practical Rule

Use Attractor to decide what the graph means and why it is trusted. Use a graph database to query a verified graph once that meaning is established.
